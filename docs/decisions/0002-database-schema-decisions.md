# 0002 - Database schema decisions (build-order step 2)

Date: 2026-08-04

## Context

Designing the Postgres schema underlying every later step (ingestion,
matching, rules, review). Recorded per the project's "flag decisions that
are hard to reverse later" working rule.

## Decisions

**UUID primary keys**, not bigint identity. This backend is designed to be
called as a tool by OpenClaw (build-order step 10) - IDs get passed around
in that interface (`run_id`, `item_id`, ...). UUIDs avoid exposing
sequential counts and don't require a round-trip to get an ID before
referencing a row in the same transaction. Reversible in principle but
would touch every table - a deliberate up-front choice, not deferred.

**Models live inside the module that owns the concept**
(`modules/ingestion/models.py` has `RawLineItem` + `UnitLookup`,
`modules/matching/models.py` has `ProductMatch`, etc.), not in one
monolithic models file. `Supplier` and `ListRun` are the exception - they
live in `db/core_models.py` since every module references them and no
single module owns them. `db/models.py` is a thin aggregator that imports
everything so Alembic and tests see the full `Base.metadata` without
modules importing each other directly. Matches the "clearly separated
internal modules" principle in CLAUDE.md's architecture section.

**`product_matches` is one row per `(supplier_id, supplier_item_number)`,
not one row per run.** This is the persistent mapping CLAUDE.md requires -
enforced with a unique constraint, verified with a test that a duplicate
insert raises `IntegrityError`. Confirmed matches get looked up and reused
on future runs from the same supplier, never re-created.

**`amazon_data_snapshots` is one row per `(list_run, raw_line_item)`,
always freshly inserted, never upserted.** CLAUDE.md is explicit that live
data is fetched fresh every run and never cached as a static assumption -
snapshots stay queryable per-run for historical comparison rather than
being overwritten.

**`classification_results.rule_trace` is `NOT NULL`.** CLAUDE.md requires
the owner always sees the reasoning behind a classification, not just the
label - making the trace optional at the schema level would allow that
requirement to be silently skipped by a future code change. Note for
whoever touches this next: passing `rule_trace=None` in Python stores the
JSON literal `null` (valid JSONB data), which does *not* violate this
constraint - only omitting the field does. Caught by
`tests/test_db_models.py` initially failing on exactly this before the
test was fixed to omit the field instead.

**FK constraint naming convention omits the referred table name**
(`fk_%(table_name)s_%(column_0_name)s`, not the more common recipe that
appends `_%(referred_table_name)s`). Two of this schema's real foreign
keys (`classification_results.amazon_data_snapshot_id`,
`classification_results.rules_config_id`) produced names over Postgres's
63-byte identifier limit with the referred table name included, which
Postgres truncates silently rather than rejecting - not acceptable for a
system whose audit trail depends on unambiguous constraint names.
`table_name` + `column_0_name` is already unique per constraint, so
nothing is lost.

**Alembic's autogenerated `downgrade()` does not drop Postgres native ENUM
types**, only the tables that used them (`CREATE TYPE`/`DROP TYPE` are
separate objects from `CREATE TABLE`/`DROP TABLE` in Postgres). Confirmed
this the hard way: running `downgrade` then `upgrade` against local
Postgres failed with `DuplicateObject: type "source_file_type" already
exists`, because the orphaned type from the first `CREATE TYPE` was still
there. Fixed by hand-adding explicit `sa.Enum(name=...).drop(...,
checkfirst=True)` calls at the end of `downgrade()` in the initial
migration (`alembic/versions/4028e416c123_initial_schema.py`) for all ten
enum types. **Anyone adding a new enum column in a future migration needs
to add its type drop to that migration's `downgrade()` by hand** -
autogenerate won't do it.

**Local dev database access needs no AWS credentials.**
`Settings.database_url` (env var `DATABASE_URL`) is a full-URL escape
hatch that, when set, bypasses `db_secret_name`/Secrets Manager entirely -
used by `backend/docker-compose.yml` (local Postgres, host port 5433,
since port 5432 is occupied by an unrelated project's container on this
machine) and `.env.example`. Must stay unset in any real environment,
where the password always comes from the RDS-managed Secrets Manager
secret fetched fresh per connection-string build (never cached, since RDS
rotates it automatically).

**`unit_lookup` table exists now with no seed data.** The table structure
is part of the schema (CLAUDE.md calls out `DP`/`ST` needing a lookup, not
a hardcoded assumption of their meaning), but populating it and wiring it
into actual normalization logic is build-order step 4, not step 2.

## Verification

Applied and reverted against local Docker Postgres (not RDS - AWS
credentials still aren't configured on this machine; infra/ hasn't been
applied yet). Full cycle actually run, not just asserted: `alembic upgrade
head` → `alembic downgrade base` → `alembic upgrade head` again, table and
enum-type counts checked at each step via `psql`. Four pytest tests
exercise the ORM layer against that same database: supplier → run → line
item relationship round-trip, the `product_matches` unique constraint, and
the `rule_trace` `NOT NULL` constraint. `pytest` passes 4/4. Re-verify
against real RDS once `infra/` is applied.
